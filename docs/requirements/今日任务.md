# AI开发思考



### AI 的优势

- 知识广、调用快
- 信息压缩和重组能力强
- 生成和改写速度快
- 局部任务执行强
  - 比如写一段脚本、sql、一个函数方法
- 试错和迭代成本低
  - 快速给出初稿
- 适合作为高频超级助手

### AI 的短板

- 无法天然理解你脑中的真实意图
- 容易脑补和过度补全
- 长任务一致性差
- 缺少稳定全局心智模型
- 逻辑看起来合理不代表真的对
- 对隐性约束不敏感
- 对输入质量和执行框架高度敏感

### 要发挥 AI 作用，核心规则是

1. 减少妄想，对齐规范
2. 系统任务拆分为单个独立的闭环任务
3. 先校准理解，再开始执行
4. 规范要变成可执行约束
5. 允许发挥，但必须限定边界
6. 任何结果都必须验证
7. 关键决策由人确认
8. 上下文要结构化，不要堆料
9. 用 harness 管执行，而不是只靠 prompt





## AI使用的思考

- 如果不表述清楚，清晰传达，人与人之间也无法达到100%传递，甚至就算表达清楚了，不同的角色不同的人理解也不一样，所以一旦进行传递肯定会有细微偏差，这部分内容时不可避免的。
- 每个人对于同一段话肯定会有不同的理解，所以一个任务两个人做，做出来的东西一定是不一样的，而这部分偏差也恰巧是人类每个人都独一无二的根本，灵机一动的想法也是从这里来的。所以我们应该允许AI具有强大的理解和执行能力，但同时不能要求它百分百如臂指使，那样的话它就只能是个工具，永远也无法进化。
- AI是一个能力强大的超级助手，对于单独的某个技术某个知识可以有非常深刻的了解，这点比任何人类都强，但是对于技能升级成任务乃至整个系统，没有统一的心智模式，任务越大，越容易偏离方向，同样的输入内容也也多，输出也就越不一致。
-  所以需要解决的问题是：
  - 如何传达你的需求，既让AI能了解，又不会过于复杂过于细节
  - 给这个强大的助手，套上harness，让它按照想要的方向进行，尽量不要产生偏移
  - harness负责代理循环、模型调用、工具路由、交接、审批、追踪、恢复和运行状态整个链路



## Harness

### 核心理念



- **AI开发工作流**
- **设计先行**
- **追溯机制**
- **Review机制**
- **反馈机制**





解决问题：

1. 仓库代码非常大时，怎么做到部分代码探索，如何限定范围，哪些内容不需要读取
2. 任务中断，换人换终端都可以无缝继续执行
3. 没有按照预定工作流执行

### harness的关键

- 需求设计阶段：使用头脑风暴和边界问题补充，充分完善需求的合理性和具体
- 规格文档设计阶段，根据头脑风暴内容和充分阅读技能规范，在规格文档的设计上引入真是的前后端规范乃至测试规范，保证规格文档能够指导计划的进行
- 原型设计阶段：根据规格文档设计出来原型界面，快速查看成果和需求偏移，原型作为辅助/原型为figma，根据原型生成代码
- 设计时必须充分读取公司技能规范，设计具体代码时需要保证设计模式，不能过分冗余，也能进适度复用，复用原则是什么，如何保证设计模式的准确合理，社区有没有什么可用规范
- 设计保证代码生成的下限，测试迭代保证代码的上限
- 使用单元测试、E2E测试、浏览器实际内容读取来快速修复问题，关于浏览器的社区技能实践，哪些比较好用？
- 一直强调Review，Review不同内容的标准是什么，如果没有标准Review的结果依然是有问题的
- 如何保证Harness的对话嵌入，这里可以实现技能验证和工作流验证



1. 默认会引入复用历史代码，甚至是git提交中的历史记录，实际上应该读取的上下文不包括这些，需要纯净的读取然后生成
2. 注册hooks，使用简单化的工作流，每轮注入必须加载的上下文
3. Review机制
4. 校验机制
5. 遇到问题如何解决机制

| 控制理论概念      | AI 开发中的对应物                                      |
| ----------------- | ------------------------------------------------------ |
| 被控对象 Plant    | 代码库、需求文档、测试环境、运行系统                   |
| 控制器 Controller | AI Agent、工作流编排器、任务规划器                     |
| 目标值 Setpoint   | PRD、Spec、验收标准、接口契约、UI 设计稿               |
| 当前输出 Output   | 当前代码、测试结果、页面表现、接口行为                 |
| 传感器 Sensor     | 单元测试、E2E、Lint、类型检查、日志、截图、人工 Review |
| 误差 Error        | 当前实现与目标之间的差距                               |
| 执行器 Actuator   | 代码修改、生成文档、运行命令、创建迁移、回滚变更       |
| 扰动 Disturbance  | 需求变更、LLM 幻觉、上下文污染、依赖异常、测试不稳定   |
| 反馈 Feedback     | 测试失败、运行报错、Review 意见、用户确认              |
| 稳定性 Stability  | 多轮迭代后系统能收敛，而不是越改越乱                   |
| 鲁棒性 Robustness | 即使模型犯错、环境异常、需求模糊，也不会破坏主流程     |
