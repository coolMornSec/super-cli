# 前端测试执行规范

## 适用范围

- 所有前端相关的测试设计、测试实现、测试补强、测试评审与验证活动。
- 所有前端需求到测试映射、TDD 口径选择、测试命令选择、E2E 预算判断与验证结论输出。

## 目标

- 用最小、最稳、最便宜的证据证明已批准行为。
- 明确区分“开发期定位”“阶段验收”“完成前验证”三种目的，避免把不同目的的测试混成一轮轮重跑。
- 明确区分“环境阻塞”“契约/框架问题”“业务行为问题”“证据不足”四类失败，避免把环境失败误判成产品失败。

## 核心原则

- 测试必须证明当前 change 已批准的行为，不得为未批准行为补写“先行测试”。
- 每个需求点都必须先判断最低可证明层级，再决定落到契约校验、单元测试、组件/集成测试还是 E2E。
- 开发期默认使用聚焦、低成本、反馈快的命令；验证期才运行正式验收集；完成前再执行最终门禁集。
- 不得把同一条命令在未新增有效证据的情况下反复重跑。
- 当测试不稳定、行为异常或根因不清时，必须切换到系统化调试，而不是继续堆叠补丁式测试。
- E2E 只在验证阶段用于跨路由、回流、真实浏览器行为和高风险集成边界的验证。

## 环境前置

- Windows 环境下首次运行 Vitest、Playwright 或依赖 esbuild 的命令前，必须先执行 `node scripts/fix-esbuild-permissions.mjs`。
- 若 Vitest、Playwright、Vite 或相关命令因 `EPERM`、浏览器启动失败、端口占用、服务启动超时而失败，不得直接重试，必须先判断是否为环境阻塞。
- 若修复脚本执行后仍出现 `EPERM`，或确认浏览器/服务无法正常启动，视为环境级阻塞，必须记入 `workflow-state.md` 的 `Blockers`，并通知用户。
- 同一条测试命令若首次失败已被识别为环境问题，不得连续第二次直接重跑；必须先进入环境修复分支。

## 测试目的分层

### 1. 开发期验证

- 目标：快速定位和收敛问题，不追求一次性覆盖全部验收链路。
- 默认命令：聚焦单测、聚焦组件/集成测试、必要的契约校验、受影响模块的类型检查。
- 默认禁止：把全量 E2E 当作日常红绿循环。
- 例外：若实现计划已明确某条需求只能由浏览器链路证明，允许运行单条定向 E2E，但不得扩散为整套 E2E 回归。

### 2. 阶段验收验证

- 目标：在 `verification` 阶段证明本次 change 的关键行为已闭环。
- 默认命令：需求-测试矩阵中约定的最小验收集，通常为“受影响聚焦测试 + 类型检查 + 单条关键 E2E”。
- 不要求：重复执行开发期已稳定通过、且与本次改动无关的整套测试。

### 3. 完成前验证

- 目标：支持 `finish` 门禁。
- 默认命令：独立 Verification Agent 约定的最终命令集。
- 要求：必须记录真实命令、真实输出、剩余风险和未覆盖点。

## 失败分类与分流

### 环境阻塞

- 典型现象：`EPERM`、浏览器无法启动、服务起不来、端口冲突、网络不可达、测试依赖进程超时。
- 处理动作：停止当前测试层，进入环境修复或挂起；更新 `workflow-state.md` 的 `Blockers`；不得继续记为产品失败。

### 契约 / 框架问题

- 典型现象：路由语义不符、UI 组件事件不符、HTTP 封装语义错误、共享状态边界错误。
- 处理动作：回退到契约校验层，先确认真实运行时语义，再继续业务测试。

### 业务行为问题

- 典型现象：断言失败、页面状态流转错误、回流不一致、字段校验错误、删除保护缺失。
- 处理动作：回退到最低可证明层；优先组件/集成测试，其次单元测试；仅在确有必要时保留到 E2E。

### 证据不足

- 典型现象：同一条测试反复执行但没有新增信息，或靠临时日志才能判断结果。
- 处理动作：停止继续重跑；写出书面结论；删除临时探针；将问题转化为最小稳定断言。

### 最低可证明层级判定顺序

当同一需求可被多个层级证明时，默认按以下顺序选择首个“能稳定证明且成本最低”的层级：

1. 契约校验
2. 单元测试
3. 组件 / 集成测试
4. E2E

## 测试分层口径

### 契约校验

- 适用于：HTTP 客户端、路由回流、表单规则、共享状态、UI 组件关键事件等框架或基础设施能力。
- 要求：业务测试前优先确认真实语义。
- 禁止：在未确认真实契约前直接补业务失败测试。

### 单元测试

- 适用于：纯逻辑判断、数据映射、工具函数、状态计算、格式化器、权限判定函数。
- 要求：逻辑隔离明确、强框架依赖已剥离。
- 禁止：把强依赖框架语义的页面编排硬拆成多个伪单测。

### 组件 / 集成测试

- 适用于：真实 DOM、组件联动、表单联动、局部交互反馈、页面容器级状态流转、回流刷新、一致性验证。
- 要求：优先使用真实挂载、真实语义驱动和标准 harness / fake / contract probe。
- 默认定位：前端页面主测试层。

### E2E

- 适用于：跨路由、回流、真实浏览器行为、关键主链路、高风险集成边界。
- 要求：必须在需求-测试矩阵或实现计划中写清进入理由。
- 禁止：把本可由更低层稳定证明的逻辑错误压入 E2E。

## TDD 适用口径

### 总原则

- 行为代码必须 TDD：业务规则、状态流转、API payload 映射、表单校验、删除/保存/批量操作、数据转换、编码生成和权限判断，必须先写失败测试，再写实现。
- 结构和配置产物不强制红绿 TDD，但必须有明确验证命令和风险记录。
- 禁止把业务逻辑伪装为结构产物来逃避 TDD。

### 严格 TDD

- 适用于：纯逻辑、纯计算、纯映射、无强框架依赖的函数或对象。
- 要求：先写失败测试，再写实现，再跑通过。

### 粗粒度前端 TDD

- 适用于：表单规则、容器级状态、composable、局部工作流。
- 允许：用一个粗粒度组件/集成测试覆盖多个紧耦合对象，而不是逐个拆分细粒度红绿循环。
- 要求：优先真实依赖，避免手工 `vi.mock` 第三方框架能力。

### 装配层豁免

- 适用于：页面骨架装配、纯布局、无状态透传、只读渲染。
- 允许：不为装配层单独创建失败测试。
- 要求：在需求-测试矩阵中标注 `N/A（装配层，由集成测试覆盖）`。

### 结构 / 配置产物例外

以下内容不强制红绿 TDD，但必须通过自动化验证或明确命令证明：

- Maven / Gradle POM
- Dockerfile
- Spring Boot Application 启动类
- `application.yml`、环境配置、i18n resource
- Vue 文件式路由装配页
- 自动生成类型声明
- 无业务逻辑的模块骨架

使用例外时，必须在 `implementation-readiness.md` 或实现计划中记录：

```md
TDD Exception:
- File:
- Reason: structural/configuration artifact
- Verification command:
- Risk:
```

如果结构文件中包含业务分支、状态流转、数据映射或用户可见行为，则该文件的行为部分仍必须由测试覆盖。

### 探针优先豁免

- 适用于：跨组件不同步、DOM 时序竞态、异步刷新不一致、根因尚不明确的前端问题。
- 允许：先做探针取证，再补最小回归测试。
- 禁止：在根因不明时盲写失败测试来“钉住”现象。
- 进入探针取证后，必须遵守《日志取证与退出门禁》。

## 框架依赖与 Mock 约束

- 禁止手工 mock 框架核心能力、运行时主接口和基础设施主入口，例如路由核心对象、HTTP 主封装、共享状态核心封装、UI 库关键行为。
- 允许使用仓库统一提供的标准 fake、harness、contract probe。
- 组件/集成测试应尽量使用真实组件挂载与真实语义驱动，而不是伪造框架生命周期。

## 日志取证与退出门禁

- 探针取证只服务于定位根因，不服务于长期维持验证链路。
- 以下任一条件满足时，必须立即停止继续添加日志：
  - 已能明确说出失败层与根因方向，例如“数据在 X 组件进入时正确，在 Y 更新后变成错误值”。
  - 同一位置的探针已运行 2 次且没有新增结论。
  - 临时探针累计超过 5 处。
- 停止后必须按顺序执行：
  1. 写出一句书面结论，说明当前根因判断。
  2. 删除全部临时探针，不得保留到提交或正式验证。
  3. 将结论转化为最小稳定检查，优先顺序为：契约断言、容器级集成断言、组件断言、纯逻辑单元断言。

## 测试预算与熔断

- 每个 change 在 `implementation-readiness.md` 或正式实现计划中必须定义测试预算。
- 同一测试文件的聚焦命令最大连续执行次数为 3 次。
- 同一条 E2E 主链路最大执行次数为 2 次。
- 同一类环境失败一旦被明确识别，不允许继续“直接重跑”测试命令；必须先执行环境修复动作。环境修复完成后，才允许重新执行一次原命令验证修复结果。
- 若“修改代码 -> 重跑测试”循环超过 3 轮仍未定位根因，必须切换到探针取证，不得继续盲改。
- 超过预算后必须立即执行以下动作：
  1. 记录失败现场，包括错误信息、断言不匹配内容、相关环境日志。
  2. 更新 `workflow-state.md` 的 `Blockers`，写明测试文件、失败模式和当前判断层级。
  3. 按失败类型回退：
     - 环境问题：转环境修复或挂起验证。
     - 契约问题：回退到契约校验层。
     - 页面行为问题：回退到组件 / 集成层。
     - 高风险浏览器行为问题：保留到验证阶段的单条 E2E 继续处理。

## E2E 启动前置条件

- 已有更低层的主要受影响测试通过，且这些测试确实覆盖了非浏览器部分的核心逻辑。
- 已确认服务可启动、浏览器可启动、端口和依赖环境正常。
- 已明确本次 E2E 要证明的单条主链路，不能以“顺便看看”作为运行理由。
- 已确认当前失败若出现，能够被归类为环境问题、契约问题或业务问题之一。

## 设计与计划要求

- `implementation-readiness.md` 或正式实现计划中必须包含需求-测试矩阵。
- 需求-测试矩阵至少写清需求点、测试目的、最低证明层级、聚焦命令、预算上限和必要的补充验证。
- 若某项需求进入 E2E，必须说明为什么不能由更低层测试稳定证明。
- 若测试策略、验证边界或命令口径不清晰，必须先补齐计划或回到规格澄清，不得靠边写边试确定策略。

## 实现要求

- 写业务实现前，必须先确认关键框架能力、依赖接口和组件语义的真实契约。
- 页面级、工作流级和强交互需求，默认优先建立容器级集成测试，不默认要求逐层细粒度失败测试。
- 只有纯逻辑、纯计算、纯映射类对象，才要求严格先写失败的单元测试。
- 当需求涉及复杂 UI 时序、跨组件状态同步或回流问题时，允许先进行探针取证，确认根因后再补最小回归测试。
- 调整实现后必须同步维护相关测试，不得保留已失真、已降级或口径变形的断言。

## 评审与验证检查

- 审查需求-测试矩阵是否完整，是否明确测试目的、最低证明层级、聚焦命令和预算上限。
- 审查是否把大量本可由单元或组件/集成测试覆盖的问题压入 E2E。
- 审查是否把环境失败误记成产品失败，或把同一环境失败反复重跑。
- 审查正式验证记录是否写清运行了什么命令、观察到什么结果、还有哪些剩余风险或缺口。
- 审查是否仍保留临时日志、临时探针或靠日志肉眼判断的验证链路。
- 证据不足、分层不清、预算失衡或环境阻塞未分流时，不得给出“测试规则满足”的结论。
