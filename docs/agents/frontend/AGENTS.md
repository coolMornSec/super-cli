# 前端执行规范

## 适用范围

- 所有前端页面、页面级组件、布局骨架、表单页、详情页、列表页与页面级交互改动。
- 所有前端相关的 `design`、`writing-plans`、`implementation`、`code-review`、`verification` 阶段。

## 执行原则

- 前端实现必须以当前 change 已批准的 OpenSpec 文档为准，不得在实现时临时发明页面结构、文案或交互规则。
- 未经需求明确授权，不得擅自新增无有效信息增量的标题、说明区、空态文案、分组块或提示文案。
- 处理页面骨架时，优先复用标准页面结构组件，不得因担心默认标题、默认文案或默认交互而绕开标准骨架。
- 若标准组件存在默认标题、默认文案或默认交互，必须先核实真实行为，再决定保留、关闭或回到规格澄清。
- 关键代码逻辑必须带标记注释，说明关键判断、边界处理或状态切换意图。
- 不得为了“更简洁”“更干净”而牺牲公司组件、标准骨架、既定交互或规格约束。

## 页面可见元素审查

- 所有页面可见变化都必须按结构元素、交互元素、文本元素三类分别审查。
- 新增文本元素前，必须先回答“它是否为用户提供当前任务、当前对象或当前状态的有效信息”。
- 仅重复控件类型、区块类型或页面通用名词的标题，视为无效信息增量，不得新增。
- 能表达当前页面任务、当前操作状态或当前业务对象的标题，可以保留或新增，但必须与当前页面语义一致。
- 若标题承担入口区分、回流识别、状态表达或任务确认作用，应视为有效信息，而不是机械判定为冗余文本。

## 标题与骨架约束

- 禁止新增纯装饰性、低信息量、与区块类型重复表达的标题。
- 允许使用能够说明页面目的、页面状态或业务对象的标题，例如“新增菜单”“编辑菜单”“菜单详情”这类具有明确语义的标题。
- 不得因为需求未逐字写出标题，就直接放弃标准页面骨架；应先判断该标题是否具有有效信息价值。
- 若标准骨架组件可以安全关闭默认标题或默认文案，必须基于真实能力判断，不得主观猜测。
- 若标准骨架无法满足当前页面语义，应先回到 OpenSpec 或设计澄清，不得直接手工拼装降级结构替代。

## 设计与计划要求

- `design` 或 `implementation-readiness` 中必须记录本次页面可见元素审查结论。
- `writing-plans` 中必须写清组件选型结论、默认文案处理方式、允许修改范围与禁止扩展范围。
- 若页面交互、文案、结构边界仍不明确，必须停止推进并回到 `brainstorming` 更新 OpenSpec。

## 实现要求

- 实现时只允许落已批准文档覆盖的页面结构、交互与文案。
- 不得使用原生 HTML 控件替代应使用的公司组件或 Element Plus 组件。
- 不得用临时占位、最小可运行页面或简化骨架替代正式页面实现。
- 遇到组件能力不确定、默认行为不明确或页面语义冲突时，先核实组件真实能力，再决定实现路径。

## 评审与验证检查

- 审查是否新增了需求未定义且没有有效信息增量的文本性元素。
- 审查标准结构组件是否被错误回避、手工替代或降级实现。
- 审查是否因“怕多标题”或“怕默认内容”而过度收缩，导致放弃标准页面骨架。
- 审查前端实现是否与当前 change 的页面语义、组件选型和可见元素审查结论一致。
- 未完成以上检查时，不得给出前端规则满足的结论。
