# 前端界面与测试架构通用规范

本文档用于收敛两类高频失误：

1. 因“需求未明确”而擅自补充页面标题、提示语等可见文本，或反过来因过度收缩而绕开标准骨架组件。
2. 因缺少测试分层，把大部分需求都压到 E2E，导致 TDD 循环过慢、定位成本过高、开发反馈失真。

## 一、页面可见元素增量审查

前端页面在设计与实现前，必须把“用户能看到的变化”拆成三类：

- 结构元素：布局容器、返回骨架、分栏、页签容器、表格骨架、列表骨架。
- 交互元素：按钮、返回动作、搜索输入、分页、选择器、确认框、禁用态。
- 文本元素：标题、按钮文案、提示语、标签、占位符、空态文案、表头文案。

### 1.1 基本判定规则

- 需求文档未明确要求的区块标题元素不得擅自新增，页面标题比如表单新增编辑这种是合理文本
- 标准结构组件在不新增额外文本的前提下必须优先复用，不得因“怕多出标题”而放弃 `MgBackWrap`、`MgLayout`、`MgPageTable` 等标准骨架。
- 若标准组件会默认引入文本或交互，必须先查真实文档、类型声明或组件实现，再明确采用以下哪一种：
  - 直接保留：该文本或交互本身就是需求要求的一部分。
  - 显式关闭：组件支持通过 `props`、`slot` 或配置关闭默认文本。
  - 回到规格：组件默认行为会新增需求未定义的可见内容，且无法安全关闭。

### 1.2 设计阶段必须产出的结论

涉及页面骨架时，`design` 或 `implementation-readiness` 中必须写出“页面可见元素增量审查”：

- 选用了哪些标准结构组件。
- 每个组件会不会新增文本。
- 若会新增文本，文本是否来自需求；若不是，如何关闭。
- 若未使用标准结构组件，原因是什么，是否已确认不存在同体系候选组件。

### 1.3 决策模板

每个高阶页面组件都按下面模板记录一次：

```md
- 组件：MgBackWrap
  角色：结构 + 返回交互
  默认新增文本：否 / 是（写清默认 title、默认按钮文案等）
  默认新增交互：是（返回）
  本次处理：保留返回，关闭标题文本
  结论：允许使用
```

### 1.4 典型反例

- 需求文档没写“页面标题”，于是完全不用标准返回骨架，改成手工拼页面头部。
- 看到 `title` 这个 prop 就默认组件一定要求标题，未核对真实默认值与 slot 能力。
- 为了“页面干净”把标准结构组件换成原生 `div`，结果失去统一回流、页头或布局能力。

## 二、测试分层与 E2E 预算

测试必须按“最低成本、足够证明”的原则分层，不得把所有需求都放进 E2E。

### 2.1 默认分层

- 单元测试：纯函数、数据归一化、请求参数组装、状态计算、校验规则、删除保护、分页回退等纯逻辑。
- 组件 / 集成测试：表单禁用态、按钮显隐、组件间联动、插槽结构、局部交互、组合函数与页面组件之间的绑定。
- E2E：跨路由跳转、页面回流、关键主链路、框架组件真实集成边界、破坏性操作确认、浏览器级行为。

### 2.2 需求到测试层的选择规则

每个需求点都必须先判断“最小可证明层级”：

- 纯逻辑，不涉及 DOM 与路由：优先单测。
- 需要真实 DOM，但不依赖跨路由或完整浏览器：优先组件 / 集成测试。
- 同时涉及路由、页面装配、回流、浏览器交互或多组件真实集成：才进入 E2E。

如果一个需求点能被更低层级稳定证明，却仍被放进 E2E 主循环，必须在计划里说明原因，否则视为测试架构不合格。

### 2.3 E2E 适用边界

E2E 主要用于以下场景：

- 页面入口与路由可达性。
- 新增、编辑、删除后的页面回流与定位恢复。
- 标准框架组件的真实联动边界，如树、分栏、页面级表格、页签。
- 需要浏览器级确认的交互，如二次确认、焦点、权限拦截、跨页状态延续。
- 高风险主链路的端到端验收。

以下场景默认不应先写 E2E：

- 纯 DTO 归一化。
- 请求参数拼装。
- 表单字段只读/必填这类局部规则，若能在组件层稳定验证。
- 删除保护、空页回退、排序计算等纯状态逻辑。

### 2.4 TDD 反馈时间预算

实现计划必须把测试命令拆成三层：

- 聚焦快速命令：单测或组件/集成测试，作为日常红绿主循环。
- 聚焦 E2E 命令：只覆盖当前正在实现的关键页面链路。
- 全量回归命令：在任务完成或阶段收口时执行。

若一个需求点的日常红绿循环只能依赖耗时较长的全页 E2E，则必须先下沉测试层级，或把 E2E 拆成更小的聚焦链路。

### 2.5 建议的需求-测试矩阵写法

`implementation-readiness` 或实现计划中的矩阵至少写清：

- 需求点名称。
- 最低可证明层级。
- 为什么不是更低层。
- 聚焦命令是什么。
- 全量回归命令是什么。

示例：

```md
- 需求点：主页面保存后树名称同步
  最低可证明层级：组件 / 集成测试
  进入 E2E 的原因：同时要求验证路由回流与真实树刷新
  聚焦命令：npm run test:component -- menu-page
  聚焦 E2E：npm run test:e2e -- -g "主页面保存后回流"
  全量回归：npm run test:e2e -- tests/e2e/menu-management.spec.ts
```

## 三、评审与验证关注点

代码评审与验证时，必须额外回答以下问题：

- 页面是否新增了需求未定义的文本性元素。
- 标准结构组件是否被错误回避，或被手工替代。
- 是否存在“为了不加标题而放弃标准骨架”的过度收缩。
- 需求-测试矩阵是否把大部分逻辑错误地压到了 E2E。
- 当前 E2E 用例是否主要覆盖跨路由、回流与高风险主链路，而不是替代全部低层测试。

只要以上任一项回答不清楚，就不能给出“规范满足”的结论。
