Bug 详细清单（按严重程度排序）

# 严重度 Bug 名称 症状 根因 修复
1 🔴 CRITICAL Mock API params 参数名错误 编辑页完全空白，Vue 应用未渲染；控制台报 TypeError: Cannot read properties of undefined (reading 'id')，导致 Vite 进程崩溃 vite-plugin-mock v3 将路径参数 (:id) 合并到 query 对象而非 params。源码 dist/index.mjs:83 显示: query = urlMatch(reqUrl).params || {} — 路径参数被赋值给 query 变量，response 函数接收的是 {url, body, query, headers}，根本没有 params 字段 3 个端点 (GET /:id, PUT /:id, DELETE /:id) 将 params 改为 query
2 🔴 CRITICAL Dev Server 端口冲突 agent-browser 连接 5173 报 ERR_CONNECTION_REFUSED；curl 却返回 200 — 因为服务器实际在 5174 上一个 Vite 进程崩溃后成为僵尸进程，仍占用 5173。新进程自动跳到 5174。agent-browser URL 硬编码 5173 lsof -ti :5173 | xargs kill -9 清理僵尸进程后重启
3 🟠 MAJOR Vite Mock 缓存中毒 重启服务器后 mock 数据仍保留删除操作后的状态（日志管理消失，菜单管理/角色管理消失） vite-plugin-mock 将 TS 文件打包缓存到 node_modules/.vite/，重启不清理缓存，直接使用旧的打包产物（其中内存已变异） rm -rf node_modules/.vite 清除缓存后重启
4 🟠 MAJOR useConfirm API 不工作 删除确认对话框弹出，点击"确定"后回调不执行，菜单未被删除 Magus 框架 useConfirm 返回 UseConfirmReturn 接口: (fn) => Promise 或 (successMessage, fn) => Promise。传入 (message, callback) 的调用方式与签名不匹配 用户明确要求"不使用 useConfirm，直接用 ElMessageBox" → 替换为 ElMessageBox.confirm()
5 🟠 MAJOR 浏览器运行旧代码 编辑 page.vue 后（useConfirm → ElMessageBox），删除仍不生效 — 对话框弹出但点确定无反应 Vite HMR 不会对已打开的页面进行完全的代码替换；浏览器缓存了旧版本的 JS bundle。agent-browser 导航到同一 URL 也可能使用缓存 需要 agent-browser navigate 强制重新加载（或清除浏览器缓存）
6 🔵 MINOR router.back() 后主页面空白 新增/编辑保存成功后 router.back() 返回主页面，页面显示空白（仅 devtools toggle 可见） Vue Router 的 back() 恢复历史栈中的组件实例，但组件 onMounted 不会重新触发。若组件在离开时被销毁，重新挂载时可能存在时序问题 需要添加 onActivated (keep-alive) 或使用 router.replace 并强制刷新数据
7 🔵 MINOR 树刷新不同步表格 点击树组件"刷新"按钮后，树数据更新但表格数据不变 @reload-tree="loadTree" 只绑定 loadTree，缺少 queryData 调用 应在 loadTree 完成后也调用 queryData，或刷新按钮同时更新两者
8 🔵 MINOR 表格搜索不生效 在搜索框输入"角色"后点击查询，表格仍显示全部3条记录 agent-browser fill 命令通过 CDP 设置 value，可能未触发 Vue v-model.trim 所需的 input 事件；type 命令追加了字符导致 value 加倍 ("角色角色") 未完全修复 — 需要进一步验证 MgSearch 组件的搜索触发机制
9 🔵 MINOR agent-browser ref 过期 点击 @e24 但实际是另一个元素（ref 在 snapshot 之间失效），导致操作错误的节点 agent-browser 的 @eN ref 在每次页面变化后失效 — 这是设计行为。缺乏严格的 "每次交互后重新 snapshot" 纪律 流程改进: 每次交互后必须重新 snapshot 再获取 ref

四、根因分析（3个关键问题）

🔴 根因 #1: 外部库 API 假设错误

问题链: 假设 vite-plugin-mock 的 response 参数有 params 字段 → 3个端点使用 params → 编辑页崩溃 → 用户报告"父节点不能删除"（实际是 TypeError）

为什么之前没发现: 类型检查通过（params 类型是 Record<string, string>，与 query 类型相同）；lint 不会检查 mock 文件；无单元测试覆盖 mock API

预防措施: 使用第三方库 API 前，读取其类型定义或源码确认参数结构，不依赖命名猜测

🔴 根因 #2: 浏览器端验证流程缺陷

问题链: 编辑代码 → Vite HMR 部分更新 → 浏览器运行混合新旧代码 → 测试结果不可靠 → 误判 bug 状态 → 反复"修复"

为什么之前没发现: Vite HMR 在开发中通常是透明的，但 agent-browser 的自动化测试无法感知页面是否使用了最新代码；没有在编辑后做硬刷新

预防措施: 每次代码修改后，用 agent-browser navigate（非 back()）强制重新加载页面

🔴 根因 #3: Mock 数据状态污染

问题链: 内存 mock 数据被操作修改 → Vite 缓存打包后的 mock 文件 → 重启服务器后缓存命中 → 数据未重置 → 测试环境不一致

为什么之前没发现: 以为重启 Node 进程会清空所有内存状态，未考虑 vite-plugin-mock 的文件系统缓存机制

预防措施: 在测试脚本开头添加 rm -rf node_modules/.vite；或使用文件持久化 mock 数据重置端点

五、经验教训 & 改进建议

📌 流程改进

  • 在使用不熟悉的第三方库 API 前，阅读其源码/类型定义而非猜测参数名
  • agent-browser 测试前清理 Vite 缓存: rm -rf node_modules/.vite
  • 每次代码修改后强制刷新浏览器（navigate 而非依赖 HMR）
  • 检查端口占用: lsof -ti :5173 | xargs kill -9 作为测试前置步骤
  • Mock API 添加一个 GET /api/menu/reset 端点用于测试间重置数据
  • agent-browser snapshot 后立即使用 ref，不跨交互缓存 ref 值

📌 做得好的地方

  • 完整的 Trellis brainstorm 流程确保用户参与所有关键决策

  • type-check + lint 在实现阶段就捕获了大部分类型错误
  • agent-browser snapshot 机制提供了可追溯的测试证据（截图存档）
  • mock 数据包含业务规则校验（编码唯一、子节点不能删等）
  • 使用 MgLayout/MgTree 等标准组件保持代码一致性
