# Magus Workflow Task

## 定位

本技能是**任务工作流路由器**，用于将用户请求按轻重程度分流到不同工作流，并在需求、规格、实现三者之间保持一致性。

本技能只做四类事：

1. 判断当前请求属于哪一级工作流
2. 决定当前阶段应该输出什么产物
3. 决定什么时候从需求层升级到开发准备层
4. 在需求发生补充或实现偏移时，保持需求文档与规格文档可追溯、一致、同步

## 核心原则

- **每次对话时必须先说明当前是哪个工作流的什么阶段**
- **`magus-pattern-guard` 必须全程调用，覆盖 L1-L4 全部阶段，用于持续识别反模式、越权抽象、职责混杂、跳步与隐式副作用**
- **L1 处理一切闲聊、通用咨询、仓库相关问答**，不要求与仓库直接相关
- **L2 处理分析、比较、判断、建议**，目标仍是“给出判断”，不进入需求整理
- **L3 只处理需求本身**，把模糊需求整理为标准需求、优化已有需求、总结需求模板
- **L4 处理基于需求的开发准备与实施编排**，生成任务规格、contracts、计划、拆解、验证与交付所需产物
- **L4 的完整阶段、产物、门禁、流转、回滚和完成规则只在 `./levels/L4-standard-dev.md` 中维护**，本文件只负责路由与一致性
- 只要用户目标仍是“把需求写清楚、写规范、写成模板”，即归入 L3
- 一旦用户目标转为“基于需求开始开发准备”，就升级到 L4
- L3 与 L4 之间必须保持单一事实源，避免需求与规格分叉
- L3 是需求真源，L4 是派生执行真源；两者通过版本号或确认标记保持一致
- 若在 L4 发现需求缺失或实现偏移，不直接回写 L3，而是在规格层显式标记并提示用户确认是否回到 L3 更新需求

## 级别定义

### L1 → 闲聊 / 通用咨询 / 仓库相关问答

#### 适用场景

- 用户随便闲聊
- 用户问与仓库无关的问题
- 用户问仓库相关内容，但只是在了解、解释、确认概念
- 任务目标不明确，尚不能进入分析或结构化处理
- 需要先沟通澄清输入信息

#### 输出产物

- 简短回答
- 解释说明
- 澄清问题
- 对话式建议

#### 不做什么

- 不要求结构化需求文档
- 不要求规格说明
- 不要求开发计划
- 不要求代码实现

---

### L2 → 分析咨询 / 判断建议

#### 适用场景

- 比较方案优劣
- 评估设计是否合理
- 分析风险、边界、取舍
- 判断某个方向是否值得做
- 给出建议，但不需要形成正式需求文档

#### 输出产物

- 分析结论
- 对比结果
- 风险点
- 推荐建议
- 备选方案

#### 不做什么

- 不整理成需求模板
- 不产出规格说明
- 不进入开发执行

---

### L3 → 需求整理 / 需求优化 / 需求模板沉淀

#### 适用场景

- 将模糊需求整理成标准需求
- 基于现有需求优化当前需求文档
- 从多个同类型需求总结某领域需求模板
- 补充需求边界、约束、异常情况、验收口径
- 只围绕“需求”本身工作，不进入开发准备

#### 输出产物

- 标准化需求文档
- 优化后的需求描述
- 需求模板
- 需求结构
- 目标、范围、边界
- 用户故事
- 场景描述
- 业务规则
- 验收口径
- 例外情况
- 非功能需求

#### 明确不产出

- 任务规格说明
- 开发计划
- 技术方案
- 实施拆解
- 研发排期
- 测试计划

#### L3 的一致性要求

- L3 必须作为需求层的唯一事实源
- 后续 L4 只能引用 L3 的需求，不得私自改写原始需求
- 若在 L4 中发现需求疏漏，优先在规格层记录偏移，并提示用户是否回到 L3 更新需求
- 只有在用户显式确认回写时，才将补充内容升级为 L3 需求变更
- L3 与 L4 之间必须维护变更记录，标记新增、修改、删除项
- 任何新增的约束、边界、例外、验收项，都必须同步到变更记录中
- 同步时建议使用需求编号、段落编号或版本号进行追踪
- 若 L3 与 L4 出现不一致，以最新显式确认版本为准，而不是静默覆盖

---

### L4 → 基于需求的开发准备 / 任务规格 / 计划 / 实施

#### 适用场景

- 用户明确要基于 L3 的需求进入实际开发
- 生成任务规格说明
- 生成实现方案与开发计划
- 拆解开发任务
- 评估影响范围
- 准备测试与验证
- 进入标准项目生成或标准开发流程

#### 输出产物

- 任务规格说明
- 技术方案
- contracts
- 开发计划
- 任务拆分
- 验收标准映射
- 测试计划
- 验证步骤
- 风险与依赖说明
- 里程碑安排
- 交付说明
- 偏移清单
- 需求对比结果

#### 特征

- 需求已经具备可执行性
- 产物面向开发交付
- 开始考虑实现路径、验证路径和风险路径
- L4 必须加载 `./levels/L4-standard-dev.md` 并在 `workflow-state.md` 记录必要技能和场景技能加载状态
- L4 的所有补充必须能回指到 L3 的需求来源
- L4 在发现偏移时应显式提示用户当前规格相对需求发生了变化

#### 版本与一致性要求

- L4 只能派生，不可替代 L3
- L4 若补充了需求信息，必须先记录为偏移，再提示用户是否回写 L3
- L4 产物应引用需求编号、段落编号或版本号
- L4 与 L3 的差异必须通过变更记录显式呈现，而不是隐式覆盖

---

## 需求与规格的一致性机制

当 L4 实现过程中发现 L3 需求存在疏漏时，必须执行以下流程：

### 1. 识别

先判断这个信息属于哪一类：

- 需求本体的补充
- 规格层的实现补充
- 测试层的验证补充
- 风险层的执行补充

### 2. 归档

如果属于需求本体补充，则先在 L4 规格中记录为偏移，不直接回写 L3。

### 3. 提示

L4 必须明确提示用户：当前规格相对原始需求发生了偏移，询问是否回到 L3 更新需求文档。

### 4. 选择

若用户选择回到 L3，则更新需求文档并重新生成 L4 规格。

若用户选择继续落盘，则在 L4 规格文档中保留偏移内容，并显式列出变更点。

### 5. 标记

为每次补充记录以下信息：

- 补充来源
- 补充原因
- 补充时间
- 影响范围
- 是否影响验收标准
- 用户确认状态

### 6. 同步

同步更新以下内容：

- L4 规格说明
- 偏移清单
- 需求对比结果
- 验收标准
- 测试点
- 风险说明

### 7. 冻结规则

当进入 L4 后，L3 的原始需求应尽量保持稳定；如必须变更，只有在用户显式确认后才回写 L3，而不是静默修改。

### 8. 单一事实源规则

- 需求真源在 L3
- 规格真源在 L4
- L4 只能派生，不可替代 L3
- 若 L3 与 L4 存在冲突，以显式记录的最新确认版本为准

## 路由决策树

按顺序判断，首个满足条件的级别即为当前级别。

### Step 1 → L1

满足以下任一情况：

1. 用户闲聊或通用咨询
2. 问题与仓库无关
3. 问题与仓库有关，但只需解释、确认、回答
4. 输入信息明显不足，需要先沟通

→ 进入 `./levels/L1-chat-and-qna.md`

### Step 2 → L2

满足以下任一情况：

1. 用户要求分析、比较、建议、判断
2. 任务不需要形成正式需求文档
3. 不需要进入开发准备
4. 只是评估方案、风险或取舍

→ 进入 `./levels/L2-analysis-and-advice.md`

### Step 3 → L3

满足以下任一情况：

1. 用户要写需求
2. 用户要优化需求文档
3. 用户要总结同类需求模板
4. 用户要补需求边界、规则、验收口径
5. 当前工作仍停留在需求表达层

→ 进入 `./levels/L3-requirements.md`

### Step 4 → L4

满足以下任一情况：

1. 用户明确要根据 L3 需求开始开发
2. 需要生成规格说明、计划、拆解、验证等开发准备产物
3. 需要进入标准项目生成或标准开发流程
4. L4 实现过程中发现必须补充需求并同步规格

→ 进入 `./levels/L4-standard-dev.md`

进入 L4 后，必须立即读取 `./levels/L4-standard-dev.md`。若无法证明该文件与必要技能已经加载，必须停止，不得生成计划、代码、评审或验证结论。

## 升级规则

- L1 可升级到 L2、L3 或 L4
- L2 可升级到 L3 或 L4
- L3 可升级到 L4
- L4 不可降级回 L3 作为默认回退，但可以通过显式需求变更返回 L3 补充后再继续
- 升级依据是用户目标与产物成熟度，而不是文件数量或口头措辞

## 完成门禁

宣称任务完成前，必须满足：

- 产物已经落位到文件或代码，而非只停留在对话中
- 已区分已验证、未验证、待确认三类条目
- L4 任务有规格记录、验证记录或等价说明
- 风险、边界、兼容性影响至少有一行说明
- 已明示宿主能力限制
- 遵守仓库 `AGENTS.md` 与用户已确认项
- 若 L4 中补充了需求，偏移清单已记录并由用户确认处理路径
- 若存在版本变化，版本号或确认标记已更新并可回查
