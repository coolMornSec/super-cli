# 公司标准

## 作用

该技能提供所有任务默认加载的跨阶段质量基线。



## 工程质量标准

- 变更范围必须与已批准的功能或缺陷边界一致。
- 优先写清晰的验收标准，而不是模糊的“已完成”描述。
- 用户可见行为、接口或流程变化时，必须同步更新相应文档。
- 倾向于清晰的文件边界，避免一个文件承担过多职责。
- 当已有批准标准时，“最小实现”“轻量实现”“临时占位”都应视为失败。
- 不得为了通过测试、构建或评审而弱化实现。
- 不得通过改写测试来掩盖实现与规范的不一致。
- 前端中的公司组件与框架规范属于发布门禁，而不是建议项。

## 测试与评审标准

- 测试应覆盖目标行为，而不只是 happy path。
- 评审先指出风险、回归和缺失验证，再谈总结。
- 审查结论应明确说明是否存在需求漂移、测试缺口、回归风险与建议动作。
- 当审查发现计划越权、需求漂移或关键风险时，应先澄清证据与影响，再请求用户确认下一步动作。

## 验证标准

- 验证记录必须说明运行了什么、观察到什么、还缺什么。
- 验证结论必须能追溯到真实证据，而不是仅依据代码阅读或口头描述。
- 当验证结果存在剩余风险或覆盖缺口时，必须明确记录，不得用模糊表述掩盖。

## 沟通规则

- 对假设保持明确。
- 当决策会影响风险、维护成本或用户体验时，要主动说明权衡。
- 在隐式产品决策出现前先升级沟通，不要自行拍板。
